# Versions

There is exactly one source for the program version: `version.txt` in the repository
root. It is part of the git release, unlike `.env`, which survives a program update and
would therefore keep the version of the release that has created it. The database version
has its own source: the `config` table of the database itself. Never write a version
literal into the code, into `config.yaml` or into the config numbers.

## Micro and minor version

`version.txt` holds the **micro** version with four parts:

```
CODE_VERSION=0.0.3.0
UI_VERSION=0.0.3.0
```

- **micro version** (four parts, e.g. `0.0.3.0`): the version of the program code. The
  fourth part is the build number and changes with **every commit**, so that the update
  and the upgrade scripts can tell one code change from the next. It is shown in the page
  footer and on the server admin page.
- **minor version** (three parts, e.g. `0.0.3`): the version of the json format and of the
  database structure. It changes **only** if the json format or the database structure
  changes, and then the micro part starts again at `.0`. A raised minor version needs a
  matching database upgrade script in `db_check` (see `db_upgrade_0_0_4`), because every
  pod with the old database version runs it on the next start.

`src/main/php/cfg/const/env.php` reads `version.txt` and derives both:

| const | value | used for |
| --- | --- | --- |
| `SYSTEM_CODE_VERSION` | `0.0.3.0` | the backend program version |
| `SYSTEM_UI_VERSION` | `0.0.3.0` | the frontend program version |
| `SYSTEM_MINOR_VERSION` | `0.0.3` | `def::PRG_VERSION`: the version of the json exports and of the database |
| `SYSTEM_PAGE_VERSION` | `0.0.3.0`, `0.0.3` in a test run | the version shown in the page footer |

`def::NEXT_VERSION` and `def::FIRST_VERSION` are not the current version but the anchors of
the database upgrade path, so they stay fixed literals.

## In a test run the footer shows the minor version

About 400 html snapshots under `src/test/resources/` contain the footer, and the footer
contains the version. If the footer showed the micro version during a test run, every
commit would change all of them. Therefore `test/test_const.php` defines `SYSTEM_TEST_RUN`,
which makes `SYSTEM_PAGE_VERSION` the minor version; outside a test run the footer shows
the micro version of the running code. So a micro release changes no test file, and a minor
release changes the snapshots on purpose - they then have to be regenerated by the
developer, never by an LLM (see `docs/llm/testing.md`).

## Where a version is read

- backend and frontend code version: `version.txt` (via `SYSTEM_CODE_VERSION` /
  `SYSTEM_UI_VERSION`); the server admin page reads the file directly, because it must also
  work if the program or the database is broken
- json export / import and the database structure: `def::PRG_VERSION`, the minor version
- the version the database has now: the `config` table (`config::VERSION_DB`), read and
  written by `db_check`
