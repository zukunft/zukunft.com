# wikidata import (2026-11-11)

The prompt "wikidata link" of `docs/llm/pending.md`: the numeric values of a phrase are imported from wikidata the
way the description is taken from wikipedia, with a confirm page before anything is written. The tables were
written before the first code edit; the line numbers are those of the start state (commit `b98d0ccd1`, the files of
the plan are unchanged in the working tree). The six steps of the prompt are six changes, each its own commit, but
all of them use this one log file, as the developer has decided in the prompt (`pending.md:88`), so the table
"Expected changes" has one row per step instead of at most three.

## Request

The converter `cfg/import/import_wikidata.php::convert` (`:234-275`) turns the entity json and the property json of
wikidata into an import json, and `unit/wikidata_tests.php` checks it offline on the two examples in
`test/resources/import/wikidata/cache/unit/`: Q72, the population (P1082) of Zurich, and Q4917, the price (P2284) of
the US dollar. The converter reads the labels of the units and criteria from a `test_paths` folder
(`item_label`, `:462-478`), skips some claims without a message, names every phrase by its wikidata label instead of
the phrase of the pod with the same wikidata reference, writes a unit of its own as a triple "entity in unit"
(`import_json`, `:320-350`), and no user can start it: the refresh icon of a wikidata reference only creates a
refresh job (`web/ref/ref.php::refresh_job_link`, `:574`).

The target: the refresh icon of the wikidata reference of a phrase opens an import preview with the words, triples
and values that wikidata would add, and only the confirmed import writes them, as the user and with the source
wikidata (`sources::WIKIDATA`). Open decisions of the developer, asked before the code of the step that needs them:

- step 3: which seed words get a property reference, e.g. inhabitants with P1082 and price with P2284, and whether
  the seed keeps one wikidata reference per wikidata id (Q4917 is the reference of the two seed triples "US dollar"
  and "U.S. dollar", `system_unit_test_data/currencies.json:792-822`)
- step 4: whether a price that matches only the reverse currency pair is reported, or imported as 1/x with the
  reverse pair

## Lessons learned by llm

1. Before a new write path is designed, read how the sibling changes reach the backend: every confirmed change is
   written in the process of the frontend (`db_object::update`, whose api put is still a TODO), and an api put of the
   frontend is a server to server call without the token of the session, so it is refused in production. The api put
   of step 5 cost three test runs and a decision of the developer that one grep for the existing write would have
   avoided.
2. A branch that a test skips in test mode (`url_with_wikidata_refresh`, the confirm) is first executed by the run of
   the developer, so `php -l` and the snapshot tests say nothing about it. Each run then showed only the next fault
   (a private `phrase::view_id`, the api put, the missing source), because the later asserts of a workflow depend on
   the confirm. Such a path is traced by reading before the hand over: the visibility of every call on another
   object, the write that the confirm triggers, and what the importer requires of the json.
3. A message that collects independent problems is never the message of a load: `phrase::row_mapper_sandbox` maps
   nothing on an earlier error, so the claim message made every phrase and value of the US dollar "new". The Q72
   fixture without a reported claim hid it; a function that takes a message is tested with a fixture whose message
   already carries an error.
4. A name of the database is never composed: a triple without name is named by `triple::generate_name`
   (`<from> (<to>)` for the verb "is a"), and a loaded triple keeps its name in `triple_name`, while `name_given()` is
   null. Both rules are in `docs/llm/coding.md` and were broken anyway, which only the read tests on the seed showed.
5. An import json that the code builds follows the same rules as an import file (`docs/llm/json_structure.md`): it
   declares every object that its values use, the source included. A read test that checks the declarations of the
   built json would have found the missing source without a write run.
6. Two checks with one message text cost a run: the origin and the session token guard both answered "did not
   originate from this site". A unique message per check made the next run decisive, while the guess from the timing
   (1448 s after the login, just after the php session lifetime of 1440 s) was wrong; a guess is named as a guess and
   the next run is made to decide it.
7. Every change goes through Edit or Write, also an appended section of a docs file: the note on the job buttons in
   `docs/llm/pending_prio_2.md` was appended with a shell heredoc, against the rule of the developer.
