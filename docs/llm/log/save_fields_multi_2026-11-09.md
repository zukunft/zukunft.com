## Lessons learned by llm

1. **A cause outside the step becomes a request of its own.** The log check of `value_write_tests` failed on one
   wrong table, and run by run the step took in the texts of the internal errors, the internal errors in the api
   answer with the pickup of the frontend, the table id of the preloaded change fields and the table of a change
   row. Each change was right, but the step grew from one expected table to four requests on top of each other,
   whose line numbers refer to uncommitted states and which the developer can no longer review one by one. For
   the expected table: when the cause of a failing assert lies outside the planned files, write it as a new prompt
   to `docs/llm/pending.md` and stop, instead of fixing it in the same step.
2. **Check the reading side with the raw rows before doubting the write.** Three runs went into the writing side
   (the owner, the user row, the p4 fixture of the update), until the listing of the change rows showed that the
   row of field 283 had been written all along and only the mapper named the wrong table. When a check shows wrong
   data, the first diagnostic lists the database rows as they are; only if they are wrong, the write is the cause.
3. **A fact derived from a name format breaks where another producer writes the name.** The table of a change row
   was parsed from the digits of the change field name, which only the database view added; the csv loader of the
   unit tests, the dummy and `set_field` each built the name in their own way, and the guess "keep the table that
   is set" hid the gap. The rule of `docs/llm/architecture.md` (the preloaded field names its table) was already
   there, but only the writing side used it. For the expected table: when a value is derived from a name or a
   format, list every producer of that name and read the value from one source.
4. **A new builder test can be an old test with other data.** Two new user row insert tests built the same
   prepared statement as an existing test, so the unique name check failed and `AUTO_UPDATE_TEST_FILES`
   overwrote a committed fixture twice; and the negative "no sql" test assumed that two equal objects give no
   insert, which the insert comparison never promised. Before a new test of a builder, search for an existing
   test whose type list gives the same query name; a negative case tests the decision that keeps the caller from
   the builder, not an assumed empty result of the builder.
5. **A counted error without its text is lost.** The run reported "8 internal errors", but the database
   recreation of the run had removed the `sys_log` rows, and the 2 test errors of the 12:22 run were overwritten
   by the console. This is lesson 3 of `docs/llm/log/row_mapper_guard_2026-11-09.md` again: first make the text
   reach the output, then guess the cause. Every place that counts an error also keeps its text, and a cause named
   without the text is reported as a guess, like the row of `change_field_by_name_and_id.sql`.
6. **A switch for a test belongs to the test.** The developer corrected the general `$sys->log_test_only` to a
   setting test by test (lessons learned by human). A flag on `$sys` changes every request and every test of the
   run, also the ones that test the error path. For the expected table: a new flag on `$sys` gets its own row with
   the reason why a parameter of the call or a setting of the single test is not enough.
